## 当前理解

- 需求目标：把 `dreaminaq` 从“看起来可以替代 App 的脚本”治理成完整 mock 实验室；脚本只模拟官方 CLI 与队列边界，真实提交继续由 `dreamina-scheduler App` 承担。
- 本期成功标准：形成可交接方案，明确 mock 覆盖范围、P0 安全门禁、状态语义、App/CLI 边界、后续 mock vs App 对比验收。
- 主要非目标：本期不继续修全部脚本、不迁移任务库、不让脚本接管正式生产。

## 已确认结论

- 短期正式生产继续使用 `dreamina-scheduler App`。
- `dreaminaq` 目前不能被视为正式生产工具。
- VIP 模型必须硬禁。
- 缺省模型必须硬禁。
- 远端生成完成即可算成功，本地下载不是成功条件。
- 脚本侧立即切到完全 mock 方向，不做真实付费提交。
- 调度器 App 是当前唯一真实提交入口。
- mock CLI 必须尽量完整模拟真实 CLI 的可观察输入输出、状态流、错误和边界条件。
- mock 与 App 真实提交后续要做对比闭环，差异反哺 mock。

## 推荐假设

- 在本方案 P0 验收通过前，agent 不应通过 `dreaminaq` 提交正式付费任务。
- `dreaminaq` 默认 CLI 路径应指向 mock；真实 CLI 路径即使保留，也必须被显式实验开关隔离。
- mock 默认使用确定性 fixture，便于复现边界问题和面板输出。
- `dreaminaq` 的 status 应新增面向 agent 的摘要输出，而不是让技能拼装状态。
- `dreaminaq monitor` 可以保留但降级为 debug。
- `dreaminaq` 与 App 的数据互通是另一个中期需求，不应塞进本期。
