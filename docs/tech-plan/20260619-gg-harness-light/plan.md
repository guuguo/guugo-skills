# gg-harness 轻量需求方案

# 一、目标与范围

**需求来源：** 当前对 `by-harness` 演进问题的讨论，以及对 Harness Engineering “地图、目标、验收、分工”思想的重新校准。

**目标：** 新建一个维护在 `guuguo-skills` 中的 `gg-harness` 技能，用更轻的方式提供 AI 项目交付马具。它不复刻当前 `by-harness` 的重运行时、任务状态机和升级脚本，而是专注薄版项目地图的审计与确认制维护、深度需求拷问、已确认目标事实文档和独立验收标准。执行层由用户在后续自行指定具体技能、插件或人工流程承接；`gg-harness` 不负责拆任务、实现、验收执行、过程态或运行证据。

**文档性质：** 这是一份 `gg-harness` 的需求事实方案，不套用 `by-tech-plan` 的 L0/L1/L2/L3 技术方案格式。`by-tech-plan` 在这里只提供目标事实细查、关键风险扫描和事实完整性检查方法；人日、排期、上线/回滚、运维等工程化字段不作为需求文档默认内容。

**本期范围：**

- 设计 `gg-harness` 的核心定位和最小可用能力。
- 定义 `AGENTS.md`、目标事实文档、独立验收标准、需求确认门禁和执行层交接边界之间的关系。
- 支持评估已有混乱 `AGENTS.md` 并给出整理建议：保留有效地图信息，把细节迁移为规则索引或需求文档引用；关键改写必须经用户确认后落盘。
- 在初始化、升级 `AGENTS.md`、落地需求 `plan.md` 前引入完备的 `grill-me` 目标校准环节，避免错误目标被固化进长期马具。
- 明确 `gg-harness` 与 `by-tech-plan`、用户自选执行层、旧 `by-harness` 的边界。
- 先落需求方案文档，后续再创建 `skills/gg-harness/` 技能目录和模板。

**本期非目标：**

- 不自动迁移旧 `by-harness` 项目；如用户明确需要迁移，按子文档 `legacy-by-harness-migration.md` 由 agent 手动执行审计、推荐、确认和迁移步骤。
- 不实现 runtime update、task switch、session_close、feature_list、复杂任务 JSON 存储。
- 不创建或维护 `.harness/runs`。
- 不维护独立 `evidence.md`、运行态 progress、session ledger 或执行状态机。
- 不定义小改动/中型/大型的执行分流，不提供 `gg-harness` 自己的执行降级路径。
- 不绑定某一个具体执行层技能、插件、命令或版本细节；只维护通用交接契约。
- 不把 Java 门禁、分布式规范、QA runner 等重规则内置进 `AGENTS.md`。

# 二、能力设计

## 1. 核心判断

当前 `by-harness` 已经承担了太多职责：初始化、任务拆分、路由、运行态记录、QA、Java 规范、runtime 升级、旧仓库迁移等。它能闭环，但入口文件和技能本身越来越重，和 Harness Engineering 原始思想里的“轻地图、重目标、硬验收、分工执行”有偏差。

`gg-harness` 应从一开始选择更薄的内核：

```text
gg-harness 维护地图、需求拷问、目标事实和验收边界
执行层由用户在执行时自行选择
需求目录本身就是执行层交接材料
执行拆分默认不进入长期 specs
by-tech-plan 只提供目标事实细查和风险扫描方法
```

## 2. 产物层级

| 产物 | 角色 | 默认位置 | 维护方 |
| --- | --- | --- | --- |
| 项目地图 | 告诉 agent 项目是什么、目录怎么走、硬边界是什么 | `AGENTS.md` | `gg-harness` 审计并推荐改写，用户确认后落盘 |
| 目标事实文档 | 单个需求的目标、范围、事实依据、边界、非目标、风险和稳定规范引用 | `docs/harness/specs/<日期[-版本]-中文短名>/plan.md` | `gg-harness` 按 by-tech-plan 的目标事实细查方式引导维护 |
| 验收标准 | 需求的可检查通过条件，以及必要时对需求范围或例外持久子需求的映射 | `docs/harness/specs/<日期[-版本]-中文短名>/acceptance.md` | `gg-harness` 维护，AI 起草但关键项需要人确认 |
| 目标校准记录 | 初始化/升级/需求 `plan.md` 落地前的 grill-me 问答、推荐答案、确认结论 | `docs/harness/specs/<日期[-版本]-中文短名>/grill.md` | `gg-harness` 引导维护 |
| 持久子需求/子规格 | 例外产物。只有当某个子块具备独立长期事实价值时才创建 | `docs/harness/specs/<日期[-版本]-中文短名>/sub-<中文短名>.md` | `gg-harness` 需先说明创建理由并取得确认 |
| 执行层交接材料 | 把已确认需求和验收标准交给用户指定的执行层，说明权威文件、硬边界和待确认问题 | 需求目录本身：`plan.md`、`acceptance.md`、`grill.md`，以及例外 `sub-*.md` | `gg-harness` 只维护需求事实和验收边界，不写执行计划 |
| 稳定规范 | 跨版本通用目标、长期设计原则、最新设计规范入口 | `docs/harness/specs/_stable/` | `gg-harness` 维护索引，按需更新 |
| 稳定规则索引 | 地图、需求、验收和执行层交接的简短规则索引 | `AGENTS.md` 或必要时 `docs/harness/rules/` | `gg-harness` 给出推荐，用户确认后生成或更新 |

需求目录示例：

```text
docs/harness/specs/20260619-gg-harness轻量化/
  plan.md
  grill.md
  acceptance.md
```

其中 `plan.md` 是默认唯一需求事实文档；`acceptance.md` 是独立验收标准；`grill.md` 是目标校准记录。极小需求可以先在 `plan.md` 中记录最小通过口径；只要存在验收争议、风险较高，或用户准备把需求交给任意执行层，就应拆出 `acceptance.md`。`sub-*.md` 不默认创建，只有满足“持久子需求”条件时才进入同一需求目录。`gg-harness` 不默认创建 `evidence.md`、`.harness/runs` 或执行进度文件。

需求目录命名优先使用中文短名，让人一眼看懂：

```text
docs/harness/specs/20260619-gg-harness轻量化/
docs/harness/specs/20260619-登录体验优化/
docs/harness/specs/20260619-支付风控改造/
```

规则：

- 默认格式：`YYYYMMDD-中文短名`。
- 如果需求属于明确版本，格式为：`YYYYMMDD-版本-中文短名`。日期始终放在最前面，方便文件树按时间排序。
- 中文短名用 4-16 个汉字为宜，说明需求对象和动作，例如 `登录体验优化`、`支付风控改造`、`仪表盘增长分析`。
- 可以保留必要英文产品名、技术名或缩写，例如 `gg-harness轻量化`、`OAuth登录改造`、`API限流治理`。
- 不再默认使用纯英文 slug；只有项目规范、外部系统限制或跨平台路径兼容性要求时，才使用英文短名。
- 版本段来自用户、PRD、Roadmap、迭代名或发布计划；不要由 AI 编造。
- 没有明确版本时，继续使用 `YYYYMMDD-中文短名`。
- 同一大版本下的需求仍然各自建目录，不把多个独立需求塞进一个版本目录。
- 版本段只用于需求归属和检索，不替代 `plan.md` 里的目标、范围和边界说明。

需求如果属于明确版本，目录名必须使用日期在前、版本在后的格式：

```text
docs/harness/specs/20260619-v1.4-登录体验优化/
docs/harness/specs/20260619-2026q3-增长看板/
docs/harness/specs/20260619-r2-支付风控改造/
```

全周期通用目标、跨版本设计规范或“始终保持最新”的 spec 内容，不放进单个需求目录，统一放到稳定目录：

```text
docs/harness/specs/_stable/
  goals.md
  design-guidelines.md
  acceptance-baseline.md
  index.md
```

`_stable/` 只放长期有效、会被多个需求引用的内容，例如产品长期目标、通用 UX/设计规范、通用验收基线、架构边界和术语表。单个需求的取舍、阶段性范围、约束和风险仍然写在对应需求目录中，并在 `plan.md` 中引用 `_stable/` 的具体文件。

## 3. `AGENTS.md` 设计原则

`AGENTS.md` 只做地图，不做操作手册全文。

必须包含：

- 项目一句话目标。
- 关键目录说明。
- 工作入口：先读地图，再读需求 `plan.md` 和验收标准；只有存在例外持久子需求时，才读取对应 `sub-*.md`。
- 如果需求引用跨周期目标、最新设计规范或通用验收基线，再读 `docs/harness/specs/_stable/` 中被索引的文件。
- 硬边界：不破坏用户改动、不做无关重构、不越过验收标准、不让开发者自判通过。
- 规则索引：更细规则放到 `docs/harness/rules/`，按需读取。

不应包含：

- 大段 Java 规范。
- 复杂运行时升级逻辑。
- 完整 QA runner 说明。
- 任务 JSON 存储细则。
- 自动续跑、分支迁移、legacy 兼容规则。

`gg-harness` 必须支持维护已有 `AGENTS.md`，但不能全自动改完。它的自动化边界是“自动审计、自动推荐、用户确认后落盘”：

1. 读取现有 `AGENTS.md`，识别地图信息、硬边界、目录约定、流程细节、长期规范和过时内容。
2. 输出一份推荐整理方案：哪些保留在薄版 `AGENTS.md`，哪些迁移到 `docs/harness/rules/`，哪些进入需求 `plan.md` 或 `_stable/`，哪些建议废弃。
3. 对每类推荐说明理由、风险和不采纳的影响；无法判断是否保留的内容列入待确认项，不静默删除。
4. 可以生成 `AGENTS.md` 候选草稿或 patch 预览，但不得直接覆盖原文件。
5. 用户确认后，才将地图信息整理回薄版 `AGENTS.md`，并按确认结果创建或更新索引文档。
6. 将仍然有效但过长的流程、规范、角色说明迁移或索引到 `docs/harness/rules/`。
7. 将需求级内容迁移或索引到 `docs/harness/specs/<日期[-版本]-中文短名>/plan.md`；跨周期稳定内容迁移或索引到 `docs/harness/specs/_stable/`。
8. 输出 `docs/harness/rules/agents-map-maintenance.md` 或在当前需求 `plan.md` 中记录整理结论，不写 `.harness/runs`。

初始化或升级 `AGENTS.md` 前必须先完成 `grill-me` 校准：

- 逐项确认项目一句话目标、主要用户、关键目录、硬边界、规则索引、已有内容保留策略。
- 每次只问一个会影响方向的问题，并给出推荐答案。
- 能通过代码库、现有文档、历史 `AGENTS.md` 判断的问题，先查证再提问。
- 对用户确认过的目标和边界写入 `AGENTS.md`；对未确认但采用的推荐假设只能写入整理报告或候选草稿，不伪装成已确认事实。
- 问题预算默认不超过 8 个用户问题：P0 最多 3 个逐个确认，P1 最多 5 个可批量确认，P2 不提问只记录推荐假设。
- 如果 3 个 P0 仍无法确认项目目标、主目录或硬边界，不继续追问；输出阻塞结论和推荐下一步，不改写 `AGENTS.md` 的关键事实。

## 4. 需求确认与拆分边界

`gg-harness` 必须把“需求事实确认”和“执行层工作”分开。确认前不自动拆子需求，不生成 `sub-*.md`，也不把执行任务写进 `docs/harness/specs/`。

确认门禁：

- `plan.md` 默认以 `draft` 开始；P0 目标、范围、非目标、关键约束和验收关注点确认前，不进入执行层交接。
- 用户明确确认 `plan.md`，或明确要求“按这个需求继续执行”，才可以把需求目录作为执行层交接材料。
- 如果用户只确认了方向但仍有 P0 未决，`plan.md` 继续标为 `blocked/draft`，只能补充事实，不能拆执行任务。
- P1/P2 未确认时可以按推荐假设继续，但必须写在 `grill.md` 和 `plan.md` 的问题记录里。

子需求/子规格是否需要持久化，按下面规则判断：

- 默认不需要。多数拆分只是为了执行、并行、审查和 token 控制，应交给用户指定的执行层自行管理。
- 只有当子块具备独立长期事实价值时，才创建 `sub-<中文短名>.md`。例如：独立版本、独立验收、独立业务 owner、独立用户路径、独立外部契约、独立风险决策，或未来会被多个需求引用。
- 创建 `sub-*.md` 前必须在 `plan.md` 中说明为什么不能只作为执行拆分，并取得用户确认或显式记录推荐假设。
- `sub-*.md` 不复制主需求的背景、目标和通用约束，只写差异事实、独立边界、独立验收引用和与主需求的关系。
- 如果子块只是“第 1 步/第 2 步/前端/后端/测试”这种执行拆分，不进入 `specs`，由执行层自行管理。

这样可以保持事实源简单：

```text
默认事实源：plan.md
独立验收源：acceptance.md
目标校准记录：grill.md
执行拆分：交给用户指定的执行层，不进入 specs
例外：有长期事实价值时才创建 sub-*.md
```

## 5. 与 by-tech-plan 的关系

`by-tech-plan` 在 `gg-harness` 中只作为目标事实拷问和风险扫描的方法来源，不作为需求文档格式来源。`gg-harness` 不照搬 by-tech-plan 的 L0/L1/L2/L3 文档模板，也不要求 `plan.md` 包含人力安排、人日、排期、上线/回滚、运维方案等工程管理字段；这些内容只有在用户明确要求，或当前需求事实本身必须说明时才记录。

更准确地说，`by-tech-plan` 对 `gg-harness` 的价值是“问得细”，不是“格式重”：

- 帮助识别目标事实是否完整：目标、用户、现状、范围、非目标、约束、风险和关键取舍是否说清楚。
- 帮助发现会影响实现方向的缺失事实：数据、接口、权限、兼容、并发、安全、跨系统等风险是否命中。
- 帮助区分已确认事实、推荐假设和待确认问题。
- 不规定 `plan.md` 的章节格式，不要求写工程管理字段，不承担验收标准正文。

`plan.md` 的核心任务是把目标事实说清楚：

- 要解决什么问题，为什么现在要做。
- 面向谁，成功后的外部可观察结果是什么。
- 本期范围、非目标、版本归属和稳定规范引用。
- 已确认事实、推荐假设、待确认问题。
- 现有系统事实、约束、风险和关键取舍。
- 是否需要持久子需求；如果需要，说明判断依据。

验收标准由独立的 `acceptance.md` 负责；`plan.md` 可以引用验收文档或记录验收关注点，但不把验收表格作为内置格式要求。

推荐关系：

```text
用户需求 / PRD
  -> gg-harness 按 by-tech-plan 的目标事实细查方法产出 docs/harness/specs/<日期[-版本]-中文短名>/plan.md
  -> 用户确认 plan.md 或明确要求按该需求继续执行
  -> gg-harness 在独立 acceptance.md 维护验收标准
  -> gg-harness 输出需求目录和读取顺序，作为执行层交接材料
  -> 只有具备长期事实价值时，才额外创建 sub-*.md
```

规则：

- 极小需求可以只维护一个 `docs/harness/specs/<日期[-版本]-中文短名>/plan.md`，其中包含目标事实、边界和最小通过口径。
- 需要交给执行层、存在验收争议或风险较高的需求必须有独立 `acceptance.md`，但不默认生成持久 `sub-*.md`。
- `plan.md` 是目标事实源，不是工程项目管理模板。
- 执行层交接输入默认是已确认的 `plan.md` 加 `acceptance.md`，必要时补充 `grill.md` 和例外存在的 `sub-*.md`；执行任务拆分由用户指定的执行层生成，不写入 `docs/harness/specs/`。
- 单个 `sub-*.md` 只有在具备长期事实价值时才成为执行输入的一部分。
- 如果历史项目已有 `docs/tech-plan/`，`gg-harness` 可以建立索引引用，但新需求默认写入 `docs/harness/specs/<日期[-版本]-中文短名>/`。
- 如果需求归属于明确大版本，需求目录名必须加版本段，例如 `20260619-v1.4-登录体验优化`；没有明确版本时不编造版本号。
- 如果 `plan.md` 依赖全周期通用目标、最新设计规范或跨需求验收基线，只在正文引用 `docs/harness/specs/_stable/` 的稳定文件，不把稳定规范复制进每个需求。

需求 `plan.md` 落地前必须完成 `grill-me` 校准：

1. 先复述需求目标和本期成功标准。
2. 按决策依赖逐个拷问：业务目标、范围边界、非目标、用户路径、现有系统事实、风险、验收关注点、证据要求，以及是否真的需要持久子需求。
3. 每次只问一个 P0 阻塞问题，并提供推荐答案和判断依据。
4. P1/P2 非阻塞问题可以采用推荐假设继续，但必须写入 `grill.md` 的问题记录。
5. 如果答案能从仓库、已有文档、接口、测试或历史实现中找到，先查证，不直接问用户。
6. `grill.md` 必须在 `plan.md` 旁边落盘；没有 `grill.md` 或等价校准记录时，不应把 `plan.md` 视为可执行输入。
7. 问题预算默认不超过 12 个用户问题：P0 最多 5 个逐个确认，P1 最多 7 个批量确认，P2 不提问只写推荐假设。
8. 达到问题预算后必须停止追问并产出阶段结论：P0 未解决则 `plan.md` 标为 `blocked/draft`；只有 P1/P2 未确认时，可以按推荐假设继续，但必须在 `grill.md` 和 `plan.md` 问题记录中标注。

## 6. 与执行层的关系

`gg-harness` 不自己实现任务调度，不维护执行状态，也不复制任何执行层的过程态文件。它只在需求和验收确认后，确保需求目录本身足够清晰，可以直接作为执行层交接材料。用户后续可以选择任何执行层技能、插件、人工流程或简单直接执行；是否拆任务、如何派发、如何审查、如何保存执行过程态，都不由 `gg-harness` 规定。

边界判断：

- **需求定义不交出去。** `plan.md` 是需求权威来源，`acceptance.md` 是验收权威来源；执行层不应重新发散需求或降低 P0 验收条件。
- **执行拆分不固化。** 执行层生成的计划、任务、任务说明、检查清单属于执行计划，不是长期需求事实，不写回 `docs/harness/specs/`。
- **验收执行不内置。** 执行层可以按 `acceptance.md` 做测试、审查或人工验证；但它只能对照验收标准检查，不替用户定义“什么叫通过”。
- **过程态不接管。** 执行层自行维护进度、审查记录、执行报告和恢复信息；`gg-harness` 不复制、不索引、不再造这些过程态。
- **项目地图仍归 `gg-harness`。** `AGENTS.md` 审计、瘦身、索引化仍是 `gg-harness` 的核心能力，不交给执行层临时改写。

因此首版策略是：

```text
gg-harness 负责定义目标、地图、目标事实文档和验收标准
执行层由用户自行选择，负责执行计划、任务拆分、实现、审查和验证
gg-harness 不维护任何 builder/evaluator/runner 过程态
```

执行层交接规则：

- `gg-harness` 的 `plan.md` 是需求权威来源；交给执行层时必须明确“用户确认过的需求事实覆盖执行层默认偏好”。
- 执行层只能在 `plan.md` 确认后生成执行计划；它生成的实施计划属于执行层，不自动转成 `sub-*.md`。
- `acceptance.md` 是验收标准来源；执行层只负责对照它检查实现。
- `grill.md` 是目标校准记录；执行层不需要重走完整需求拷问，除非执行时发现 P0 歧义。
- `sub-*.md` 是例外输入；只有当某个子块已经被确认具备长期事实价值时才提供给执行层。
- 如果用户没有指定执行层，`gg-harness` 仍只交付需求和验收文档，不降级承担执行层职责。

## 7. 验收标准能力

`gg-harness` 必须把验收标准作为一等产物维护。

验收标准采用“AI 起草，人强参与确认”的方式：AI 负责从已确认或待确认的 `plan.md` 生成初稿、补齐可观察条件和验证方式；用户负责确认 P0 验收是否真正代表目标达成。中大型或高风险需求在 P0 验收未确认前，只能把 `acceptance.md` 标为 `draft`。

验收标准要求：

- 每个需求必须有可检查的验收口径。
- 如果存在持久 `sub-*.md`，每个子需求必须能追溯到至少一条验收标准。
- 能量化的条件写具体数值、命令、截图要求、日志关键字或 UI 状态。
- 模糊质量要求必须写判断方法，例如对照截图、录屏、测试输出、人工确认记录或执行层审查结论判断。
- 验收标准要区分重要性和证据要求：P0 必须能证明目标达成；高风险条件要写清测试、截图、日志、人工确认或执行层审查证据。

推荐 `acceptance.md` 结构：

```md
# 验收标准

| 编号 | 对应来源 | 验收条件 | 重要性 | 证据要求 | 状态 |
| --- | --- | --- | --- | --- | --- |
| A1 | plan.md | {总体可运行/可交付条件} | P0/P1/P2 | {相关测试/人工检查/执行层审查/截图日志} | pending |
| A2 | plan.md#某范围 或 sub-xxx.md | {范围/例外子需求条件} | P0/P1/P2 | {验证方式} | pending |
```

验收标准落地前也要经过轻量 grill：

- 追问每条验收标准是否真的代表用户要的结果。
- 追问证据要求是否匹配需求风险，避免高风险需求验收过轻。
- 追问是否存在容易被 agent “看起来完成”但实际没达标的漏洞。
- 对每条模糊标准给出推荐量化方式；用户不确认时标记为待确认假设。
- 问题预算默认不超过 6 个用户问题：优先确认验收口径和证据要求；超出部分写入推荐假设或待确认问题，不继续追问。
- 如果关键验收口径无法确认，允许先生成 `acceptance.md` 草稿，但状态必须标为 `draft`，不得作为执行层或人工最终通过依据。

## 8. 执行层交接材料

`gg-harness` 不需要额外维护独立的 `execution-handoff-template.md`。需求目录本身就是交接材料：`plan.md` 说明目标事实，`acceptance.md` 说明验收标准，`grill.md` 说明确认过程和待确认项，例外存在的 `sub-*.md` 说明长期子需求事实。额外模板会制造第二份交接事实，增加漂移风险。

交给执行层时，只需要在当轮回复中列出读取顺序和硬边界：

- 需求目录路径：`docs/harness/specs/<日期[-版本]-中文短名>/`
- 读取顺序：先读 `plan.md`，再读 `acceptance.md`，必要时读 `grill.md` 和例外存在的 `sub-*.md`
- 确认状态：`plan.md` 是否已确认，P0/P1/P2 未确认项分别是什么
- 稳定规范：按需读取 `plan.md` 引用的 `docs/harness/specs/_stable/` 文件，例如长期目标、设计规范或通用验收基线
- 验收来源：以 `acceptance.md` 为准，执行层不得自行降低 P0 验收条件
- 路径约束：执行计划和过程态由执行层自管，不写回 `docs/harness/specs/`，除非用户明确要求把执行发现同步为需求事实变更

## 9. 最小技能目录

首版 `gg-harness` 建议只包含：

```text
skills/gg-harness/
  SKILL.md
  references/
    agents-template.md
    plan-template.md
    grill-template.md
    sub-spec-template.md  # 可选，仅用于有长期事实价值的子需求
    acceptance-template.md
    stable-spec-template.md
    agents-md-audit.md
    legacy-by-harness-migration.md  # 按需读取，不进入默认初始化流程
```

暂不内置：

- `scripts/scaffold.py`
- runtime manifest
- update_runtime
- task_switch
- session_close
- QA runner

首版可以新增一个很薄的 `scripts/init_project.py`，但职责只限于：

- 审计 `AGENTS.md`，输出推荐整理方案和候选草稿；用户确认后才应用改写。
- 创建 `docs/harness/specs/` 和 `docs/harness/specs/_stable/`，必要时创建 `docs/harness/rules/`。
- 复制模板或生成索引。
- 输出整理报告。

不得引入 runtime manifest、自动升级、任务状态机或复杂 session 管理。

## 11. 首版用户路径

### 建立需求事实

```text
用户：用 gg-harness 梳理这个需求
agent：
1. 读取现有材料，并对 AGENTS.md/需求目标执行必要 grill 校准
2. 对 AGENTS.md 输出审计建议和候选草稿；涉及关键改写时等待用户确认后再落盘
3. 在 docs/harness/specs/<日期[-版本]-中文短名>/grill.md 记录目标校准结论
4. 在 docs/harness/specs/<日期[-版本]-中文短名>/plan.md 写目标事实文档
5. 在 acceptance.md 写独立验收标准草稿
6. 等用户确认 plan.md 和关键 P0 验收
7. 输出需求目录、读取顺序和硬边界，作为执行层交接材料
8. gg-harness 职责结束；后续执行由用户另行指定技能、插件或人工流程
```

### 交给执行层

```text
用户：按这个 gg-harness 需求交给某个执行层执行
agent：
1. 确认 plan.md 不是 blocked/draft
2. 确认 acceptance.md 中 P0 验收已被用户确认，或明确标记为 draft
3. 列出权威文件：plan.md、acceptance.md、grill.md、例外 sub-*.md
4. 列出待确认问题和不得自行改变的边界
5. 输出需求目录、读取顺序和硬边界，供用户指定的执行层读取
6. 后续任务拆分、实现、审查、验证和过程态全部由执行层承接
```

# 三、验证与后续落地

**文档自检重点：**

- `gg-harness` 首版技能创建后，能够通过 skill 结构校验。
- 使用一个混乱 `AGENTS.md` 演练：能先输出薄地图候选草稿和迁移建议，用户确认后再落盘，并把长规则迁移或索引到 `docs/harness/rules/`。
- 使用一个目标模糊的初始化/升级场景演练：能按 `grill-me` 规则逐项校准目标、目录、边界、验收关注点和证据要求，并生成 `grill.md`。
- 验证 `grill-me` 不会无限追问：初始化/升级最多 8 个用户问题，需求 `plan.md` 最多 12 个用户问题，验收标准最多 6 个用户问题。
- 使用一个简单需求演练：能生成薄 `AGENTS.md`、`docs/harness/specs/<日期[-版本]-中文短名>/plan.md`、`acceptance.md`，并用需求目录直接交接，不进入执行。
- 使用一个复杂需求演练：能按 by-tech-plan 的目标事实细查方法生成 `plan.md`，确认前不拆执行任务，确认后只输出需求目录读取顺序和硬边界。
- 使用一个持久子需求演练：只有当子块具备独立长期事实价值时才创建 `sub-*.md`，并能说明它为什么不是运行时执行拆分。
- 使用一个有版本归属的需求演练：能生成日期优先、带版本段的中文需求目录，例如 `YYYYMMDD-v1.4-登录体验优化/`。
- 使用一个跨周期设计规范演练：能写入 `docs/harness/specs/_stable/`，并被需求 `plan.md` 引用。
- 使用一个中大型需求演练：能把已确认 `plan.md`、`acceptance.md` 和例外存在的 `sub-*.md` 作为交接材料提供给用户指定的执行层，不让执行层重新发散需求。
- 使用一个旧 `by-harness` 项目迁移演练：只在用户明确要求时读取 `legacy-by-harness-migration.md`，能输出迁移审计、推荐方案、用户确认点和迁移报告，不运行旧自动升级脚本。
- 验证没有 `grill.md` 或等价目标校准记录时，初始化/升级/需求 `plan.md` 落地会被标记为未完成。
- 验证 `AGENTS.md` 不承载细节全集，详细规则能从 references 或 `docs/harness/rules/` 按需读取。
- 验证 `.harness/runs`、`evidence.md`、运行态 progress、session ledger 不属于 `gg-harness` 首版产物。

**后续落地步骤：**

- 第一步只提交本需求方案。
- 第二步新增 `skills/gg-harness/` 最小技能目录和 references 模板。
- 第三步用 `gg-skills-governor` 或仓库安装器把 `gg-harness` 暴露到 canonical skills。
- 第四步用一个示例仓库或临时目录做端到端演练。
